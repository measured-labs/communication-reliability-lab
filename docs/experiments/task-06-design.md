## 1. 실행하는 법

- 노트북에서: 커밋한 뒤 `SERVICES_SSH=<계정>@<.164> LOAD_SSH=<계정>@<.158> scripts/servers-sync.sh` — 두 서버의 `~/communication-reliability-lab`을 그 커밋으로 맞추고 .158에 k6를 둔다.
- 노트북의 ssh agent(서버 키를 담은)를 전달하며 .158에 들어가(`ssh -A`) 그곳에서 `SERVICES_SSH=<계정>@<.164> K6=.tools/k6-v2.4.0/k6 scripts/<실행기>` — .158에서 .164로의 ssh는 전달된 agent로 한다(키 파일을 서버에 두지 않는다). 이렇게 돌리면 노트북의 세션이 끊길 때 실행이 멈춘다(그 실행은 색인에 남지 않거나 실패로 남는다 — 조용히 이어지지 않는다).
- **긴 실행(06-b) — 노트북이 끊겨도 돌게**: 전달된 agent는 세션과 함께 사라지므로 `nohup`·`setsid`만으로는 .158 → .164의 ssh가 다음 실행부터 실패한다(agent 없이 .158 → .164는 `Permission denied (publickey)` — 2026-11-26 확인). 그래서 agent를 전달한 세션에서 **.158 → .164의 ssh 마스터 연결을 하나 열어 두고**(`ControlPersist`), 실행기를 `setsid nohup`으로 띄워 모든 ssh가 그 연결을 다시 쓰게 한다(`SERVICES_SSH_CONTROL` — `scripts/lib.sh` 머리). 마스터는 처음 한 번만 agent로 인증하고, 그 뒤로는 agent 없이 산다 — 키도 agent도 서버에 남기지 않는다. 노트북에서:
  ```
  ssh -A <계정>@<.158> 'mkdir -p ~/.crl-ssh && chmod 700 ~/.crl-ssh && setsid ssh -fN -M -S ~/.crl-ssh/m -o ControlPersist=yes -o BatchMode=yes -o ServerAliveInterval=30 <계정>@<.164> < /dev/null'
  ssh <계정>@<.158> 'cd ~/communication-reliability-lab || exit 1; SERVICES_SSH=<계정>@<.164> SERVICES_SSH_CONTROL=$HOME/.crl-ssh/m K6=.tools/k6-v2.4.0/k6 \
    setsid nohup scripts/task06-all.sh t02 > runs/task-06b-t02.log 2>&1 < /dev/null & exit'
  ```
  (`cd … && … &`로 묶으면 `&`가 목록 전체를 감싸 ssh가 실행기가 끝날 때까지 돌아오지 않는다 — 2026-11-26 스모크에서 겪음. 그때 노트북의 ssh를 끊어도 실행기는 이어 돌았다.) 끝나면(또는 그만둘 때) `ssh <계정>@<.158> 'ssh -S ~/.crl-ssh/m -O exit <계정>@<.164>'`로 마스터를 닫는다. 진행은 `runs/task-06b-index.tsv`와 위 로그로 본다. 끊기거나 멈추면 같은 명령을 다시 부른다 — 실행기가 색인에 종료 0으로 있는 반복을 건너뛰고 이어 돈다(`scripts/task06-all.sh` 머리). 알아야 할 위험: 마스터가 열려 있는 동안 .158에서 그 소켓을 열 수 있는 사람(이 계정과 root)은 .164에 이 계정으로 들어갈 수 있다 — 전달된 agent와 같은 종류의 위험이 세션보다 길게(마스터를 닫을 때까지) 간다.
- 실행 기록은 .158의 `runs/`에 쌓인다. 노트북으로 `rsync`로 가져와 앞 단계와 같은 꼴(실행 폴더의 요약 + `raw.tar.gz` — `scripts/task04-pack.sh`)로 커밋한다. 커밋 앞에 기록에 주소 전체가 들지 않았는지 찾는다(`grep -r '<주소 앞 세 마디>'` 0건).

## 2. 조용함과 시계 — 실행마다

### 2-1. load average 문턱

- **규칙**: 실행 앞(이미지 확인 뒤, 설정 기록·워밍업 앞)에 두 서버의 1분 load average를 본다. 둘 다 **논리 CPU 수(`nproc`) × 0.25 이하**(.164 ≤ 4.0, .158 ≤ 1.5)면 진행, 아니면 10초마다 다시 보며 **600초**까지 기다리고, 그래도 높으면 그 실행은 실패(종료 1 — 색인에 남는다). 값은 `LOADAVG_MAX_PER_CORE`·`LOADAVG_WAIT_SECONDS`로 바꿀 수 있고 실행마다 `config.env`에 남는다(`docs/measurement.md` 6절 task 06 칸).
- **까닭**:
  - 이 실험이 쓰는 몫: .164에서는 컨테이너 넷이 CPU 2개씩(합 8 — `compose.yaml`의 한도는 논리 CPU의 몫이다), .158에서는 k6(도착률 ≤ 100/s, 코어 1개 안팎 — 추론)와 실행 사이의 분석기(CPU 2 제한).
  - .164는 물리 코어 8에 스레드가 둘씩이다(논리 16). 우리 몫(8)이 물리 코어 수와 같아, 다른 일이 평균 4개 돌면 그 일과 우리 컨테이너가 같은 물리 코어의 두 스레드를 나눠 쓰게 될 수 있다 — 하이퍼스레드 둘이 한 코어를 나누면 스레드 하나의 처리가 느려진다(추론 — 얼마나인지 재지 않았다). 그래서 "문턱 아래면 빈 코어가 남는다"고 말할 수 없다. .158은 하이퍼스레딩이 없는 물리 6코어라 문턱(1.5) 아래면 k6와 분석기 몫(≤ 3) 밖에 물리 코어가 남는다.
  - 그래서 0.25는 다툼이 없다는 보장이 아니라 **눈에 띄게 붐빌 때 재지 않는 선**이다 — 06-a 앞에 본 두 서버의 평소 값(0.1 안팎)보다 훨씬 높고, 노트북에서 다른 프로젝트가 돌 때의 값(4~47)보다 낮다. 첫 06-a와 리뷰 뒤 재보정에서 이 문턱이 실행을 기다리게 한 적은 없다(6절 — 기다린 시간 모두 0초) — 문턱이 무엇을 막았는지는 실측이 없다. 실행마다 문턱을 본 때의 값과 끝의 값을 `config.env`에 남겨 결과 문서에서 본다.
  - 우리 실행이 남기는 몫: 06-a의 실행 사이에 잰 값(아래 06-a 결과)에서 앞 실행의 꼬리(부하·분석기)가 다음 실행 앞의 1분 값을 문턱 위로 올리지 않는지 본다 — 올린다면 문턱이 우리 자신을 기다리게 되어 시간만 든다.
  - load average는 실행할 수 있는(그리고 디스크를 기다리는) 일의 수의 지수 평균이라 순간의 몰림(수 초)을 놓친다. 실행이 끝난 뒤의 값(`host_loadavg_end`·`services_loadavg_end`)도 남겨, 실행 동안 다른 일이 끼었는지를 결과 문서에서 볼 수 있게 한다. 실행 도중에 문턱을 넘은 실행을 버리지는 않는다(넘었다는 사실을 결과 문서에 적는다).
  - 600초: 1분 값은 시간 상수 60초로 줄어 문턱의 두 배에서 문턱까지 ≈ 42초, 네 배에서 ≈ 83초다. 600초 안에 내려오지 않는 것은 꼬리가 아니라 이어지는 다른 일이다 — 그때는 재지 않는다.

### 2-2. 두 서버 시계의 어긋남

- **재는 법**(`scripts/lib.sh`의 `clock_offset`): .158에서 .164로 ssh 연결 하나를 열어 두고 20번 묻는다 — .158의 시계로 보낸 때 t0, .164가 `date +%s%N`으로 읽은 값 r, .158이 받은 때 t1. r은 t0와 t1 사이 어딘가에서 읽혔으므로 어긋남 = r − (t0 + t1)/2이고 참값과의 차는 (t1 − t0)/2 이하다. 왕복이 가장 짧은 한 번의 값과 그 반을 남긴다.
- **재는 때**: 부하 구간에 붙여 두 번 — **k6를 띄우기 바로 앞**(워밍업·상태 초기화 뒤, `clock_offset_services_minus_load_ms_start`·`clock_offset_error_ms_start`)과 **k6가 끝난 바로 뒤**(가라앉기·내보내기 앞, `…_end` 둘). 두 값 사이는 k6가 도는 시간(부하 15~50s + k6가 뜨고 내리는 몫)뿐이다. 06-a 재보정 앞의 실행(`d5027e5`…`da77c88`)은 앞의 값을 이미지 확인 뒤(워밍업 앞)에, 뒤의 값을 내보내기 뒤에 쟀다.
- **오차**: 왕복의 반은 **그 값을 잰 순간**의 상한이다 — ssh 안에서 한 줄을 주고받고 `date`를 띄우는 시간이 들어 ping 왕복(0.4ms)보다 크다(06-a의 실측은 아래). 잰 순간과 다른 때(부하 구간의 가운데 등)의 어긋남은 그 사이에 두 시계가 다르게 간 만큼 더 다르다 — 06-a에서 본 가장 빠른 움직임은 ≈ 1.7~2ms/분이었다(6절). 그 몫은 앞·뒤의 차로 보고 문턱으로 막는다(`docs/measurement.md` 12-5).
- **쓰는 곳**: 분석기가 앞·뒤의 평균만큼 서비스의 시각을 부하 서버의 시계로 옮겨, 부하 도구의 시각과 서비스의 시각을 견주는 지표(전수 — `docs/measurement.md` 12-3)를 계산한다. 결제가 실행 중에 자기 시계로 판정하는 구간 장애는 k6가 앞의 값만큼 헤더를 옮겨 보낸다(12-4). 앞·뒤의 차가 문턱(5ms)을 넘으면 그 실행은 입력 오류(종료 1)이고, 실행기(`scripts/task06-all.sh`)가 같은 서비스로 한 번 다시 돈다. 층 사이의 시각 지표는 모두 .164의 한 시계라 영향이 없다.
