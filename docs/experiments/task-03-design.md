## 0. 모든 실험에 같게 두는 것

- 자원·Tomcat·Hikari·keep-alive·연결 타임아웃 500ms: task 01·02와 같다(`compose.yaml`을 바꾸지 않는다). 플랫폼 스레드.
- 재고→결제 요청 타임아웃 1000ms(task 01의 값). 주문→재고는 실험마다 정한다(아래).
- **부하 도구의 연결 재사용을 끈다**(k6 `--no-connection-reuse`, 이번 단계의 모든 시나리오 — task 02 실험 나와 같다. 까닭: task 02 R02-1). 그래서 task 02의 실험 가·다와는 부하 방식이 다르다 — 절댓값을 견주지 않는다.
- 장애는 새 헤더 `X-Attempt-Fault`로만 넣는다(아래 2절). task 01의 `X-Fault`는 쓰지 않는다.
- 다시 시도하는 실패: 다시 시도하는 층마다 `failed`(5xx·연결 실패)와 `unknown`(요청 타임아웃·504·연결 끊김) 둘 다(계약: "일시적 실패와 타임아웃").
- 조건 하나 = 서비스를 그 조건의 설정으로 다시 띄움 → 버리는 실행 1회(`r0`) → 반복 3회(`r1`~`r3`). 실패한 실행도 표에서 빼지 않는다. 조건이 걸렸는지는 실행마다 `settings-<서비스>.json`의 `retry`(떠 있는 재시도 감싸개에서 읽은 값)와 타임아웃을 `run.sh`가 견준다.
- 실행마다 분석이 둘: task 01의 대조 분석(DB로 두 번 처리됨·잃음) + 새 `analyzer retry`(시도·도착·몰림·예산). 서버에 닿지 못한 요청(`clients.notReachedServer`)이 0이 아니면, 그리고 서비스가 센 넣은 실패의 수가 분석기가 기록에서 다시 센 수와 다르면 그 실행은 **불일치(종료 코드 2)**다.
- 멱등 키가 없다. 재시도가 만든 "두 번 처리됨"을 조건마다 DB로 센다(task 04의 출발점).

## 1. 재시도 감싸개 — 요지 (정본 `docs/retry.md`)

- 아래 층 호출(`NextLayerCall`)을 감싸는 직접 짠 코드(`chain-link/…/Retry.kt`). 라이브러리 없음. 설정 `chain.retry.*`(층마다 환경 변수 `ORDER_RETRY_*`·`INVENTORY_RETRY_*`), **기본은 꺼짐** — 꺼져 있으면 감싸개를 만들지 않는다(task 01·02의 호출 그대로).
- **최대 시도 횟수는 처음 시도를 센다**(1 = 재시도 없음).
- 간격(다음 시도 n ≥ 2 앞에서 기다리는 ms): `none` 0 · `fixed` base · `exponential` min(cap, base·2^(n−2)) · `exponential-jitter` ⌊u · min(cap, base·2^(n−2))⌋, u ~ [0, 1) 균등.
- **지터는 하나로 정했다: 위의 "full jitter"(0부터 지수 간격까지 균등).** 까닭: 식이 하나라 테스트가 범위를 정확히 견줄 수 있고, 간격의 아래 끝을 0까지 펴서 같은 순간에 실패한 요청들을 가장 넓게 흩는다. 이름과 생각은 AWS Architecture Blog "Exponential Backoff And Jitter"(2015)에서 왔다(그 글의 본문은 이번에 열지 못했다 — 식은 이 문서와 `docs/retry.md`의 것이 정본). 다른 방식(같은 크기에 ±반을 더하는 "equal jitter", 앞 간격에 기대는 "decorrelated")은 재지 않는다.
- **재시도 예산 = 부르는 쪽 프로세스 하나의 토큰 버킷**: 용량 C, 처음에 C개 찬 채로 시작. 호출(처음 시도) 하나마다 r개를 넣는다(C를 넘지 않게). 재시도 하나마다 1개를 뺀다 — 1개 미만이면 재시도하지 않고 그 시도의 결과로 끝낸다(`budget-denied`). 그래서 재시도 수 ≤ C + r × 호출 수. 출처의 생각: AWS Builders' Library "Timeouts, retries, and backoff with jitter" — "limiting retries locally using a token bucket … allows all calls to retry as long as there are tokens, and then retry at a fixed rate when the tokens are exhausted".
- 시도를 모두 쓰면 **마지막 시도의 결과**를 돌려준다(앞 시도가 타임아웃이었어도 — 이 단순한 규칙이 만드는 "실패 응답인데 처리됨"도 DB로 센다).

## 2. 넣는 실패 — `X-Attempt-Fault` (정본 `docs/measurement.md` 8-1)

| 지시 | 그 서비스에서 |
|---|---|
| `<서비스>:fail-first=<n>` | 그 requestId로 그 서비스에 **처음 n번 든 시도**는 처리하지 않고 500 |
| `<서비스>:slow-first=<n>@<ms>` | 처음 n번 든 시도는 그만큼 잔 뒤 **처리한다**(위 층이 타임아웃으로 끊어도 행이 남는다) |
| `<서비스>:outage=<시작 ms>-<끝 ms>` | 입구에 든 시각(벽시계)이 [시작, 끝)이면 처리하지 않고 500(구간 장애) |

- 헤더는 사슬을 따라 그대로 넘어가고, 서비스는 requestId마다 든 횟수를 세어 판정한다(위 층이 재시도해도, 위의 위 층이 재시도해도 같은 카운터다). 서비스가 종류마다 넣은 수를 세고(`GET /attempt-faults`), 분석기가 시각 기록(그 서비스의 입구에 든 기록)에서 기대 수를 다시 센다: `fail-first`·`slow-first` = requestId마다 min(n, 든 횟수)의 합, `outage` = 입구에 든 시각이 구간 안인 기록 수.
- 실험 가·다의 **섞음**(시나리오 `retry-mix`): 요청 i마다 u = mulberry32(씨앗 `20261125` + i·0x9e3779b9)의 첫 값으로 고른다 — 조건과 반복마다 같은 i는 같은 지시. **지어낸 분포다.**

| u | 지시 | 뜻 | 800건에서 뽑힌 수 |
|---|---|---|---|
| < 0.50 | 없음 | 정상 | 393 |
| < 0.70 | `payment:fail-first=1` | 한 번 실패 | 165 |
| < 0.80 | `payment:fail-first=2` | 두 번 | 76 |
| < 0.85 | `payment:fail-first=3` | 세 번 | 40 |
| < 0.90 | `payment:fail-first=4` | 네 번 | 47 |
| < 0.94 | `payment:fail-first=9` | 시도 상한 안에서는 풀리지 않음 | 36 |
| 나머지 | `payment:slow-first=1@1500` | 첫 시도가 재고의 타임아웃(1000ms)보다 늦게 처리됨 | 43 |

("뽑힌 수"는 실행 전에 같은 함수를 node로 돌려 센 것. 분석기도 정답에서 다시 센다.)

## 3. 지표 (정본 `docs/measurement.md` 8-3)

| 지표 | 식 |
|---|---|
| 끝내 성공한 비율 | 정답 가운데 HTTP 2xx ÷ 정답 수 |
| 응답 시간 | k6가 잰 `elapsedMs`의 분위수(nearest-rank) — 전체와 성공한 것 |
| 층이 받은 호출 수(배수) | 그 층의 시각 기록(업무 입구에 든 것) 수, ÷ 요청 수 |
| 다시 한 일 | 그 층에 든 횟수 − 그 층에 든 requestId 수(`repeatArrivals`), 처리 행이 둘 이상인 requestId(`doubled`)와 넘친 처리 행(`extraProcessedRows`) |
| 버려진 일 | 끝내 성공하지 못한 요청(2xx 아님)의 처리 행 수(`processedNotCompleted`) |
| 시도·재시도·예산 | 부르는 쪽의 시도 기록에서: 시도 수, 재시도(2번째 이상) 수, 시도마다의 결정(`success`·`not-retryable`·`retry`·`max-attempts`·`budget-denied`), 계획한 간격과 실제 간격(앞 시도의 끝 → 이 시도의 시작)의 분위수 |
| 몰림 | 결제의 입구에 든 시각을 첫 송신 시각부터 **50ms 칸**으로 나눈 칸마다의 수의 최대(`peak`) — 구간 앞·안·뒤, 그리고 재시도(2번째 이상 시도의 시작)만의 최대. 1s 칸의 최대도 |
| 구간 동안의 호출 | 결제의 입구에 든 시각이 구간 장애 안인 기록 수 |
| 회복 ① 불린 쪽 | 재시도(2번째 이상 시도)의 마지막 시작 − 구간 끝(ms, 음수면 구간이 끝나기 전에 재시도가 멎었다) |
| 회복 ② 부른 쪽 | 2xx가 아닌 요청의 마지막 송신 시각 − 구간 끝(음수면 그만큼 앞에 보낸 요청부터는 재시도가 살렸다) |
| 두 번 처리됨 | task 01의 `doubledTotal`(어느 층이든 처리 행이 둘 이상인 requestId) |
| 부하가 같았나 | 서버에 닿지 못한 요청(0이어야 함), k6가 보내지 못한 반복(0이어야 함 — `run.sh`가 실패로), 넣은 실패의 수(서비스가 센 수 = 기록에서 다시 센 수) |

**이번 장애는 시각으로 끝난다**(결제가 실제로 지쳐서 실패하는 것이 아니다). 그래서 회복 ①②는 "재시도가 구간 뒤로 얼마나 이어지나"와 "구간의 끝 몇 ms를 재시도가 살렸나"를 잴 뿐, **재시도의 부하가 회복을 늦추는가는 이 설계로 잴 수 없다**(결과의 한계에 적는다).

## 5. 실험 가 — 시도 횟수

- **바꾸는 것**: 재고→결제의 최대 시도 1·2·3·5.
- **같게 두는 것**: 섞음(2절, 40/s × 20s = 800건), 간격 `exponential` 100ms·cap 1000ms(지터 없음 — 응답 시간을 예측할 수 있게. 지터의 효과는 실험 나만 본다), 예산 꺼짐, 주문 재시도 꺼짐, 주문→재고 5000ms(재고의 재시도를 다 품는다 — 가장 긴 것은 ≈ 1.5s).
- **예상(뽑힌 수로 센 것)**:

| 최대 시도 | 성공 | 실패 / 결과 모름 | 결제가 받은 호출(배수) | 두 번 처리됨 |
|---|---|---|---|---|
| 1 | 393 (49.1%) | 364 / 43 | 800 (1.00) | 0 |
| 2 | 601 (75.1%) | 199 / 0 | 1207 (1.51) | 43 |
| 3 | 677 (84.6%) | 123 / 0 | 1406 (1.76) | 43 |
| 5 | 764 (95.5%) | 36 / 0 | 1612 (2.02) | 43 |

  - 두 번 처리됨 43 = `slow-first`: 첫 시도가 1000ms에 끊긴 뒤 두 번째 시도가 처리되고, 첫 시도도 1500ms에 처리된다. 최대 1에서는 그 43건이 "결과 모름인데 처리됨"이다.
  - 성공한 요청의 응답 시간(대략 — 처리 몫 ≈ 10ms를 더함): 정상 ≈ 10ms, 한 번 실패 ≈ 110, 두 번 ≈ 315, 세 번 ≈ 720, 네 번 ≈ 1530, `slow-first` ≈ 1110ms. 그래서 성공한 것의 p90: 최대 2 ≈ 110ms, 3 ≈ 315ms, 5 ≈ 1110ms / p99: 2·3 ≈ 1110ms, 5 ≈ 1530ms. 시도를 늘리면 성공은 늘지만 **늘어난 성공은 꼬리(p90·p99)에 쌓인다**.
  - 모든 수가 반복 사이에 같을 것이다(건수는 섞음과 규칙으로 정해진다). 다르면 도구를 먼저 의심한다.

## 6. 실험 나 — 간격

- **바꾸는 것**: 재고의 간격 `none` / `fixed` 200ms / `exponential` 100ms·cap 1000 / `exponential-jitter` 100·1000.
- **같게 두는 것**: 재고의 최대 시도 4, 예산 꺼짐, 주문 재시도 꺼짐·주문→재고 5000ms, 부하와 구간 장애.
- **부하의 모양**: **500ms마다 20건을 같은 순간에** 보낸다(40/s × 30s = 1200건, 시나리오 `retry-outage-burst`) — 같은 장애를 같은 순간에 본 클라이언트 여럿(같은 주기로 도는 일, 같은 이벤트에 반응하는 화면)을 흉내 낸다. 고르게 오는 부하에서는 실패도 고르게 나서 지터가 흩을 몰림이 없다. 결제에 구간 장애 [10s, 20s)(부하 시작 기준).
- **예상**:

| 간격 | 50ms 칸 최대(구간 안 / 앞) | 재시도만의 50ms 칸 최대 | 구간 동안 결제가 받은 호출 | 회복 ① | 회복 ② |
|---|---|---|---|---|---|
| none | 60~80 / 20 | ≈ 60 | ≈ 1600(구간에 든 400건 × 4) | ≈ −480ms | ≈ −500ms |
| fixed 200 | 20 / 20 | 20 | ≈ 1580 | ≈ +100ms | ≈ −1000ms |
| exponential | 20 / 20 | 20 | ≈ 1580 | ≈ +200ms | ≈ −1000ms |
| exponential-jitter | 20~25 / 20 | 5~12 | ≈ 1590 | 0~+200ms | ≈ −500ms |

  - 구간(10s)이 재시도가 이어지는 시간(최대 700ms)보다 훨씬 길어서, 구간 동안의 호출 수는 간격과 상관없이 거의 "최대 시도 × 들어온 요청"이다 — **간격은 합이 아니라 몰림의 모양을 바꾼다**는 것이 예상이다. 간격이 없으면 한 무리의 네 시도가 한 칸에 몰린다. 고정·지수 간격은 무리마다 따로 떨어진 칸에 20씩(재시도 물결이 첫 시도의 무리와 같은 크기). 지터는 재시도를 흩지만 첫 시도의 무리 20은 그대로라 전체 칸 최대는 20 아래로 내려가지 않는다.
  - 회복 ②: 구간 끝에 가까운 무리의 마지막 시도가 구간 뒤로 넘어가면 산다 — 재시도가 이어지는 시간이 긴 간격일수록 구간의 끝을 더 많이 살린다.
  - 반복 사이의 범위가 겹치면 "가를 수 없다"고 쓴다(특히 지터의 칸 최대).

## 7. 실험 다 — 어느 층에서

- **바꾸는 것**: 재시도하는 층(재고만 / 주문만 / 둘 다)과, 재고가 재시도할 때 주문→재고 타임아웃(재고의 재시도를 품는 3000ms / 품지 못하는 250ms).
- **같게 두는 것**: 섞음(2절, 800건), 재시도하는 층마다 최대 3·`exponential` 100ms·cap 1000, 예산 꺼짐, 재고→결제 1000ms.

| 조건 | 재시도 | 주문→재고 |
|---|---|---|
| 다-1L | 재고만 | 3000ms |
| 다-1S | 재고만 | 250ms |
| 다-2 | 주문만 | 3000ms |
| 다-3L | 둘 다 | 3000ms |
| 다-3S | 둘 다 | 250ms |

(주문만 재시도할 때는 재고가 재시도하지 않아 주문의 타임아웃이 재고의 재시도를 품을 일이 없으므로 3000ms 하나만 잰다.)

- **예상(뽑힌 수로 센 것 — 요청마다의 시각을 따라가 셈)**:

| 조건 | 성공 | 결과 모름 | 결제 호출(배수) | 재고에 든 횟수 | 두 번 처리됨 |
|---|---|---|---|---|---|
| 다-1L | 677 | 0 | 1406 (1.76) | 800 | 43 |
| 다-1S | 558 | 242 | 1406 (1.76) | 800 | 43 |
| 다-2 | 677 | 0 | 1406 (1.76) | 1406 | 43 |
| 다-3L | 764 | 0 | 1756 (2.20) | 959 | 43 |
| 다-3S | 764 | 36 | 1875 (2.34) | 1078 | 119 |

  - 다-2는 결제 호출의 배수가 다-1과 같지만 **재고가 같은 만큼 다시 일한다**(재고 행이 요청마다 시도 수만큼 — 다시 한 일 606).
  - 다-3: 풀리지 않는 실패(`fail-first=9`)에 결제 호출이 3 × 3 = 9번 — 층마다 재시도하면 맨 아래의 배수가 곱해진다.
  - 다-1S: 재고의 재시도가 주문의 250ms를 넘는 요청(두 번 실패 이상과 `slow-first`)은 주문이 "결과 모름"으로 끝내는데, 재고와 결제는 끝까지 일한다 — 두 번 실패(76건)는 결제가 처리했는데 클라이언트는 모른다(버려진 일 = 결과 모름인데 처리됨).
  - 다-3S: 주문이 250ms에 포기하고 다시 부르는 동안 첫 재고 호출이 아직 재시도 중이라, 두 번 실패(76건)가 결제에서 두 번 처리되고(재고도 둘 다 `RESERVED`), `slow-first`(43건)는 결제에서 세 번 처리된다 → 두 번 처리됨 76 + 43 = 119.

## 8. 실험 라 — 재시도 예산

- **바꾸는 것**: 재고의 예산 꺼짐 / 켬(용량 10, 호출마다 0.1 — 재시도를 호출의 약 10%로).
- **같게 두는 것**: 재고 최대 시도 4·`exponential` 100ms·cap 1000, 고르게 오는 부하 40/s × 40s = 1600건(시나리오 `retry-budget`), 결제에 긴 구간 장애 [10s, 30s), 주문 재시도 꺼짐·5000ms.
- **예상**:

| 예산 | 구간 동안 결제가 받은 호출 | 재시도 | `budget-denied` | 회복 ② | 회복 ① |
|---|---|---|---|---|---|
| 꺼짐 | ≈ 3180(800 × 4 − 끝) | ≈ 2390 | 0 | ≈ −700ms | ≈ +200ms |
| 켬 | ≈ 890(800 + 10 + 0.1 × 800) | ≈ 90 | ≈ 790 | ≈ −25~0ms | 0 근처 |

  - 예산은 긴 장애에서 결제가 받는 호출을 약 4배에서 약 1.1배로 줄이고, 그 대가로 구간 끝을 재시도로 살리는 몫(회복 ②)을 잃는다. 장애가 시각으로 끝나므로 구간 뒤의 성공은 두 조건에서 같다(3절의 한계).
  - 예산이 다시 차는 데: 호출 10개에 토큰 1개 → 40/s에서 용량 10이 차기까지 ≈ 2.5s. 구간 뒤에는 재시도할 일이 없어 부하에는 드러나지 않을 것이다.

## 9. 돌리는 시간과 줄인 것

| 묶음 | 조건 | 실행(버리는 것 포함) | 실행 하나 | 합 |
|---|---|---|---|---|
| 기본 설정 확인 | 5 실행 | 5 | ≈ 1.2분 | ≈ 7분 |
| 보정 | 5 설정, 7 실행 | 7(버리는 실행 없음) | ≈ 1분 | ≈ 10분 |
| 가 | 4 | 16 | ≈ 1.1분 | ≈ 20분 |
| 나 | 4 | 16 | ≈ 1.3분 | ≈ 23분 |
| 다 | 5 | 20 | ≈ 1.1분 | ≈ 25분 |
| 라 | 2 | 8 | ≈ 1.4분 | ≈ 12분 |

조건마다 다시 띄우는 시간까지 ≈ 1시간 50분.

**줄인 것과 이유**:
- 부하 시간을 20~40s로 짧게(task 02의 30~50s 대신) — 섞음의 건수가 규칙으로 정해져 반복 사이 흔들림이 작을 것이고, 두 시간 안에 다섯 실험을 넣으려고.
- 실험 가의 최대 시도는 넷(1·2·3·5). 4는 뺐다(5와 3 사이의 차이는 섞음의 `fail-first=3·4` 몫으로 계산된다).
- 지터는 한 방식(full jitter)만, 간격의 시작값·상한은 한 쌍(100ms·1000ms)만.
- 실험 다에서 주문만 재시도할 때의 짧은 타임아웃은 재지 않는다(7절).
- 예산은 한 값(용량 10·0.1)만.
- 결제가 지쳐서 실패하는(부하에 따라 실패가 늘어나는) 장애는 넣지 않았다 — 재시도의 부하가 회복을 늦추는 되먹임은 재지 않는다(3절).
- 보정에는 버리는 실행을 두지 않았다(기대가 건수의 전부/0과 넓은 범위).
- 멱등 키, 서킷 브레이커, 기한 전파, 취소는 넣지 않는다(task 04·05·범위 밖).
