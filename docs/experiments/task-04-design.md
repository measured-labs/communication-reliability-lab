## 0. 모든 실험에 같게 두는 것

- 자원·Tomcat·Hikari·keep-alive·연결 타임아웃 500ms·플랫폼 스레드: task 01~03과 같다. 재고→결제 요청 타임아웃 1000ms. 주문→재고는 실험마다(아래).
- **부하 도구의 연결 재사용을 끈다**(k6 `--no-connection-reuse`, 이번 단계의 모든 시나리오 — task 03과 같다).
- 바꾸는 것은 **멱등 키 켬/끔 하나**(환경 변수 `IDEMPOTENCY_ENABLED` — 세 서비스에 같은 값). 부하 도구는 키를 켜든 끄든 같은 요청(같은 헤더)을 보낸다 — 꺼진 서비스는 키 헤더를 읽지 않는다.
- 조건 하나 = 서비스를 그 조건으로 다시 띄움 → 버리는 실행 1회(`r0`) → 반복 3회. 실패한 실행도 색인(`runs/task-04-index.tsv`)에 남기고 표에서 빼지 않는다.
- 실행마다 분석: task 01의 대조 분석(DB로 두 번 처리됨·잃음) + 새 `analyzer idem`(키 지표, 넣은 끊김의 대조, 결과 모름 맞추기, 층마다의 처리 시간) + 재시도가 켜진 실행은 task 03의 `analyzer retry`. task 03의 늘 견주는 것(서버에 닿지 못한 요청 0, 넣은 실패의 대조, DB 행이 있는데 시각 기록이 없는 requestId 0, 켜진 층의 `attemptsNotArrived` 0)은 그대로 지킨다 — 재시도 분석을 하지 않는 실행(같은 requestId를 두 번 보내는 실험 나·보정)에서는 `analyzer idem`이 앞의 셋을 같은 뜻으로 견준다.
- 실행 기록에 재시도 예산의 **시작 토큰**을 남긴다(ledger R03-7 — 부하 직전 `GET /retry-budget`).

## 1. 멱등 키 — 요지 (정본 `docs/idempotency.md`)

- **키의 꼴**: 헤더 `Idempotency-Key`(IETF HTTPAPI 초안의 이름). 값은 부하 도구가 정한 문자열 — 이 실험에서는 그 요청의 `X-Request-Id`와 같은 값이다(분석기가 requestId로 묶으므로 "같은 논리 요청"이 하나의 id를 갖게). 서비스는 키를 `Idempotency-Key`에서만 읽는다. 사슬을 따라 그대로 넘어간다.
- **저장**: 층마다 자기 DB에 표 `idempotency_keys(key 기본 키(유일), request_id, row_id, amount, state, response_status, response_body, …)`. **업무 행과 같은 트랜잭션**에서 넣는다 — 주문·재고는 PENDING 업무 행을 넣는 첫 커밋에(상태 `IN_PROGRESS`), 결과를 쓰는 둘째 커밋에서 업무 행과 함께 키의 상태와 응답을 고친다. 결제는 업무 행과 키(상태 `COMPLETED`, 응답 201)를 한 트랜잭션에. 키를 넣지 못하면(이미 있음) 그 트랜잭션의 업무 행도 되돌린다.
- **다시 온 키**(이 차례로):
  1. 저장된 금액과 다르면 **422**(처리하지 않는다).
  2. `COMPLETED`·`FAILED`(그 층이 결과를 낸 것) → **처리하지 않고 저장한 응답(상태와 본문)을 그대로 돌려준다** + 응답 헤더 `Idempotent-Replayed: true`.
  3. `UNKNOWN`(그 층도 아래 층의 결과를 몰랐던 것 — 응답이 504였던 것) → 업무 행을 새로 만들지 않고 **같은 업무 행으로 아래 층을 같은 키로 다시 부른다**(이어 하기). 아래 층도 키를 가지고 있으므로 아래에서 두 번 처리되지 않는다. 결과 모름을 나중에 맞추려면(실험 라) 이것이 있어야 한다 — 결과를 모른다는 것은 "처음의 결과"가 아직 없다는 뜻이라, 504를 되돌려 주면 영원히 맞출 수 없다.
  4. `IN_PROGRESS`(처음 요청이 아직 처리 중) → **기다리지 않고 409로 거절한다**.
- **동시에 온 같은 키를 거절(409)로 정한 까닭**: ①기다리면 스레드와(행 잠금으로 기다리면) DB 연결을 쥔다 — task 02에서 스레드가 차는 것이 위 층까지 번지는 것을 봤다. ②처음 요청이 끝나지 않으면(죽음) 기다림에 또 상한이 필요하다. ③IETF 초안과 Stripe가 같은 경우에 409를 쓴다. **알고 고른 대가**: 이 저장소의 위 층은 `409`를 "아래가 처리하지 않은 실패"(`Failed:HTTP_409`, 다시 시도하지 않는 갈래)로 읽는다(`docs/measurement.md` 0절·`docs/retry.md` 2절 — 바꾸지 않는다). 그래서 위 층이 재시도하다 아래 층의 처리 중인 키에 부딪히면, 아래는 끝내 처리하는데 위는 실패로 끝난다(실험 가-2에서 센다).
- 같은 트랜잭션 안의 키 삽입은 `insert … on conflict (key) do nothing`이다. 동시에 둘이 넣으면 PostgreSQL이 뒤의 것을 앞의 커밋까지 기다리게 한 뒤 0행으로 돌려준다 — 결제(한 트랜잭션)는 이 몇 ms의 기다림으로 동시 요청이 저장한 응답을 받는다. 주문·재고는 첫 커밋 뒤 아래 층을 부르는 동안 `IN_PROGRESS`라 409.
- 켜져 있는데 키 헤더가 없거나 비면 400(행 없음). **기본은 꺼짐** — 꺼져 있으면 키 헤더를 읽지 않고 표를 쓰지 않는다(task 01~03의 동작 그대로). 실제 값은 `GET /settings`의 `idempotency`.
- 라이브러리 없음(명세 2절). 키의 만료·청소, 처리 중에 죽은 키(`IN_PROGRESS`로 남음)의 회수는 넣지 않는다(단순화 — `docs/idempotency.md`).

## 2. 새 장애 — 커밋한 뒤 응답 없이 연결을 끊는다 (R01-13)

- 헤더 `X-Drop-Fault: <service>:drop-after-commit=<n>` — 그 requestId로 그 서비스에 **처음 n번 든 것**은 처리하고 마지막 커밋을 한 뒤 **응답을 한 바이트도 보내지 않고 연결을 닫는다**. 위 층은 결과를 모른다(JDK HttpClient는 `IOException` → `Unknown:IO_…`, k6는 `status` 0).
- `X-Fault`에 kind를 더하지 않고 새 헤더로 둔다(task 03이 `X-Attempt-Fault`를 따로 둔 까닭과 같다 — `X-Fault`의 kind가 늘면 `/faults`의 키가 늘어 task 01의 분석기 계약과 그 테스트, 커밋한 실행의 다시 계산이 깨진다). "처음 n번"으로 둔 까닭: 같은 키로 다시 보낸 것(재시도, 나중의 맞추기)이 또 끊기면 맞추기를 잴 수 없다.
- 끊는 법: Tomcat의 `ActionCode.CLOSE_NOW`(응답이 커밋되기 전에 연결을 닫고 뒤의 쓰기를 버린다). 서비스는 끊을 때 센다(`GET /drop-faults`), 분석기는 시각 기록에서 다시 센다(요청마다 min(n, 그 서비스에 든 수)의 합). 끊긴 요청의 시각 기록 `status`는 0.
- 보정 섞음(아래 3절)에 세 층 모두를 넣는다. task 01의 `calibration` 섞음과 기대 파일은 그대로 둔다(꺼진 상태의 확인에 원래대로 쓴다).

## 3. 보정 — 답을 아는 실행 (실험 전에, 통과해야 수치를 쓴다)

시나리오 `cal-idem`: 16/s × 25s = 400개 요청(requestId), 재시도 꺼짐, 주문→재고 2000ms. 요청 i의 칸 = i % 8(칸마다 50개):

| 칸 | 보내는 것 |
|---|---|
| 0 | 정상 |
| 1 | `X-Drop-Fault: order:drop-after-commit=1` |
| 2 | `inventory:drop-after-commit=1` |
| 3 | `payment:drop-after-commit=1` |
| 4 | `X-Attempt-Fault: payment:slow-first=1@1500`(재고가 1000ms에 포기, 결제는 1500ms에 처리) |
| 5 | 같은 요청을 **잇달아** 두 번(둘째는 첫째의 응답을 받은 뒤) |
| 6 | 같은 요청을 **동시에** 두 번(k6 `http.batch`) |
| 7 | 같은 키로 잇달아 두 번 — 둘째는 금액 +1 |

부하가 끝나고 가라앉은 뒤 **맞추기 단계**: 정답이 결과 모름(`status` 0 또는 504)인 요청을 같은 헤더·같은 키·같은 금액으로 한 번씩 다시 보낸다(칸 1~4, 200건). 정답 줄은 400 + 150 = 550줄.

**기대(모두 섞음과 규칙이 정하는 값 — 잰 값이 아니다. 같지 않으면 도구나 구현이 틀린 것)**:

| | 키 꺼짐 | 키 켬 |
|---|---|---|
| 정답의 판정 | 완료 350 · 결과 모름 200 · 실패 0 | 완료 300 + 칸 6의 둘째 가운데 저장한 응답을 받은 것 · 실패 = 칸 7의 둘째 50(422) + 칸 6의 409 · 결과 모름 200 |
| 다시 보낸 200건 | 모두 201(새로 처리) | 모두 201(칸 1 = 주문이 저장한 응답, 칸 2~4 = 이어 하기) |
| 두 번 처리됨(DB) | **350**(칸 1~7) | **0** |
| 금액 불일치 · PENDING · 정답에 없는 행 | 0 · 0 · 0 | 0 · 0 · 0 |
| 끊긴 수(서비스가 센 수 = 기록에서 다시 센 수) | 주문 50 · 재고 50 · 결제 50 | 같음 |
| 키 행(주문 / 재고 / 결제) | 0 / 0 / 0 | 400 / 400 / 400 (상태 모두 `COMPLETED`) |
| 다시 온 키: 주문 | — | 저장한 응답 100 + 칸 6의 몫(0~50) · 409 0~50(칸 6, 둘의 합 50) · 422 50 · 이어 하기 150 |
| 재고 · 결제 | — | 재고: 저장한 응답 50(칸 2) · 이어 하기 100(칸 3·4) / 결제: 저장한 응답 100(칸 3·4) |

- 키 꺼짐의 대조 분석 기대는 `labels`(서명마다의 수)까지 정확히 적는다. 키 켬은 칸 6이 409와 저장한 응답으로 갈리는 몫이 시각에 달려 서명을 정확히 적지 못한다 — 그 칸은 둘의 합만 범위로 견준다.
- 꺼진 상태에서 task 01~03의 보정(`calibration`, `duplicate`, `cal-false-timeout` 300·1000ms, `cal-sampler`, `cal-retry-*` 일곱)을 원래의 기대 파일로 다시 돌려 통과해야 한다.
- 재기동을 넘어 키가 남는지(계약: 확인 한 번): 키를 켜고 요청 하나를 보낸 뒤 이 프로젝트의 `order` 컨테이너 하나를 다시 띄우고 같은 키로 다시 보내 `Idempotent-Replayed: true`와 행 1개를 본다(`scripts/task04-restart-check.sh`).

## 5. 실험 가 — 재시도가 만든 이중 처리

- **바꾸는 것**: 키 끔/켬.
- **같게 두는 것**: 섞음 `idem-retry-mix`(40/s × 20s = 800건 — task 03의 `retry-mix`와 같은 씨앗·같은 칸에서, "정상"의 한 몫(u ∈ [0.40, 0.50))에 `payment:drop-after-commit=1`을 넣었다. 실행 전에 같은 함수를 node로 돌려 센 수: 정상 314, 결제에서 끊김 79, `fail-first=1` 165, `=2` 76, `=3` 40, `=4` 47, `=9` 36, `slow-first=1@1500` 43), 재시도하는 층마다 최대 3·지수 100ms·상한 1000ms·예산 꺼짐.
- 조건(task 03에서 두 번 처리됨이 나온 둘):

| 조건 | 재시도 | 주문→재고 |
|---|---|---|
| 가-1 | 재고만(최대 3) | 3000ms |
| 가-2 | 주문과 재고 모두(최대 3) | 250ms |

- **예상**(요청마다의 시각을 규칙으로 따라가 센 값 — 가-2 켬의 `fail-first=2` 몫만 시각의 여유가 약 20ms라 잰 값에 가깝다):

| 조건 | 키 | 성공 | 실패 / 결과 모름 | 두 번 처리됨 | 넘친 결제 행 | 성공 아닌데 처리됨(결제) |
|---|---|---|---|---|---|---|
| 가-1 | 끔 | 677 | 123 / 0 | **122**(끊김 79 + `slow-first` 43) | 122 | 0 |
| 가-1 | 켬 | 677 | 123 / 0 | **0** | 0 | 0 |
| 가-2 | 끔 | 764 | 0 / 36 | **198**(끊김 79 + `fail-first=2` 76 + `slow-first` 43) | 241 | 0 |
| 가-2 | 켬 | **558~634** | **166~242** / 0 | **0** | 0 | **43**(`slow-first`) |

  - 가-1 켬: 끊긴 결제의 재시도와 `slow-first`의 둘째 시도가 결제에서 저장한 응답(201)을 받는다 — 결제의 `replayed` 122(79 + 43: `slow-first`는 둘째 시도가 먼저 처리하고, 1500ms에 깨어난 첫 시도가 저장한 응답을 받는다).
  - **가-2 켬에서 성공이 줄 것이다**(이 설계의 대가로 예상하는 것): 재고가 결제의 실패를 다 쓰고 `FAILED`(502)를 저장한 요청(`fail-first` ≥ 3: 123건)에 주문이 다시 부르면 저장한 502가 돌아와, 키가 없을 때는 층을 가로지른 시도로 살던 87건(`=3` 40 + `=4` 47)이 실패로 굳고 `=9` 36건은 결과 모름 대신 실패가 된다. `slow-first` 43건은 주문의 재시도가 재고의 처리 중인 키에 부딪혀 409 → 주문은 실패로 끝내는데 재고·결제는 끝내 처리한다(위 표의 "성공 아닌데 처리됨"). `fail-first=2` 76건은 재고의 첫 호출이 약 330ms에 끝나고 주문의 재시도가 약 350ms에 드는 차이에 달렸다 — 먼저 끝나면 저장한 201(성공), 늦으면 409(실패). 그래서 성공 558~634.
  - 키가 있을 때 두 번 처리됨이 0이 아니면 원시 기록(시각 기록, 키 행)으로 까닭을 확인해 적는다.

## 6. 실험 나 — 클라이언트의 중복 요청

- **바꾸는 것**: 키 끔/켬. 두 시나리오: `idem-dup-seq`(같은 요청을 잇달아 두 번), `idem-dup-conc`(동시에 두 번, `http.batch`). 20/s × 20s = 400쌍(정답 800줄), 장애 없음, 재시도 꺼짐, 주문→재고 2000ms.
- **예상**:

| 시나리오 | 키 | 두 번 처리됨 | 두 응답의 갈래 | 정해진 값인가 |
|---|---|---|---|---|
| 잇달아 | 끔 | 400 | `201+201` 400(둘 다 새로 처리) | 규칙이 정함 |
| 잇달아 | 켬 | 0 | `201+201` 400 — 둘째는 모두 저장한 응답(`Idempotent-Replayed`) | 규칙이 정함 |
| 동시에 | 끔 | 400 | `201+201` 400 | 규칙이 정함(유일 제약이 없다) |
| 동시에 | 켬 | 0 | **`201+409` 380~400**, 나머지 `201+201`(뒤의 것이 첫 요청이 사슬을 다 돈 뒤에 들어 저장한 응답을 받음) | **잰 값** — 두 요청이 주문에 드는 차이(새 연결 둘을 함께 맺음 — 수 ms 예상)와 첫 요청이 사슬을 도는 시간(약 20~30ms)의 견줌 |

## 7. 실험 다 — 키 저장의 비용

- **바꾸는 것**: 키 끔/켬. 시나리오 `idem-plain`: 장애 없음, 40/s × 30s = 1200건, 재시도 꺼짐, 주문→재고 2000ms.
- 키를 켜면 쓰기가 는다: 주문·재고는 첫 트랜잭션에 키 삽입 하나, 둘째 트랜잭션에 키 갱신 하나, 결제는 한 트랜잭션에 키 삽입 하나(유일 인덱스 포함). 트랜잭션 수는 같다.
- **예상(잰 값)**: 층마다 자기 몫 시간의 p50이 결제 +0~2ms, 재고·주문 +0~4ms. 클라이언트 응답 시간 p50 +0~8ms. p99는 반복 사이의 흔들림에 묻혀 **가를 수 없다**고 예상한다. task 03의 무리 지은 부하(C7)에서 자기 몫 p50은 주문 약 20ms·재고 약 14ms·결제 약 6ms였다(고르게 오는 40/s에서는 이보다 작을 것이다). 반복 사이의 범위가 겹치면 "가를 수 없다"고 쓴다.

## 8. 실험 라 — 결과 모름을 나중에 맞추기

- **바꾸는 것**: 키 끔/켬. 시나리오 `idem-reconcile`: 40/s × 20s = 800건, 재시도 꺼짐, 주문→재고 2000ms. 요청 i의 칸 = i % 10: 0~4 정상(400), 5 `X-Attempt-Fault: inventory:slow-first=1@2500`(주문이 2000ms에 포기, 재고는 2500ms에 처리), 6·7·8 주문·재고·결제에서 `drop-after-commit=1`, 9 `payment:slow-first=1@1500`(각 80).
- 부하가 끝나고 가라앉은 뒤 결과 모름(`status` 0 또는 504)인 요청을 같은 키로 한 번씩 다시 보낸다(20/s).
- **예상(섞음과 규칙이 정하는 값 — 이 실험이 재는 것은 끝 상태가 모이는가라는 정확성이다)**:

| 키 | 결과 모름(다시 보낸 것) | 다시 보낸 것의 2xx | 끝 상태: 세 층에서 정확히 한 번 | 두 번 처리됨 |
|---|---|---|---|---|
| 끔 | 400 | 400(새로 처리) | **0** | **400** |
| 켬 | 400 | 400(주문이 저장한 응답 80, 이어 하기 320) | **400** | **0** |

  - 끔에서 맞추기는 "되돌려 받은 응답"만 맞고 DB는 틀어진다 — 다시 보낸 것마다 아래 층(끊긴 층과 그 아래)이 한 번 더 처리한다.
  - 다시 보내기 전에 모든 층의 처리 중인 요청이 0이 된 것을 확인하므로(가라앉기), 이번 실험에는 "아직 처리 중인 키에 다시 보냄(409)"이 없다. 그것은 실험 가-2와 나가 본다.

## 9. 돌리는 시간과 줄인 것

| 묶음 | 실행(버리는 것 포함) | 합(예상) |
|---|---|---|
| 꺼진 상태의 확인(task 01~03 보정 12) | 12 | ≈ 15분 |
| 보정 `cal-idem` 끔/켬 + 재기동 확인 | 2 + 1 | ≈ 5분 |
| 가(4 조건) | 16 | ≈ 22분 |
| 나(4 조건) | 16 | ≈ 20분 |
| 다(2 조건) | 8 | ≈ 11분 |
| 라(2 조건) | 8 | ≈ 11분 |

**줄인 것과 이유**:
- 키의 만료와 청소, 처리 중에 죽은 키의 회수 — 실행마다 표를 비우는 실험이라 쓰이지 않는다(단순화).
- 동시에 온 같은 키는 거절 하나만 잰다(기다리는 방식은 재지 않는다 — 1절의 까닭).
- 위 층이 409를 무엇으로 읽나는 바꾸지 않는다(task 01~03의 규칙). 가-2에서 그 대가를 센다.
- 실험 가의 재시도 설정은 task 03의 한 쌍(지수 100·1000, 최대 3)만.
- 키 저장 비용은 한 부하(40/s, 장애 없음)에서만. 무거운 부하나 큰 표에서의 인덱스 비용은 재지 않는다.
- 키의 꼴(requestId와 같은 값)은 하나만 — 키와 requestId가 다를 때의 동작은 보정의 단위 테스트가 볼 일이다(서비스는 키를 헤더에서만 읽는다).
