> 명세 9절 task 02의 계약을 실험으로 옮긴 것. **결과를 보기 전에** 썼다(2026-11-24). 결과와 예상의 대조는 `docs/results/task-02-timeouts.md`.
> 무엇을 재려는지의 출처: 하네스 문서 `communication-reliability.md` 2절의 "잴 것" — 타임아웃 줄(불린 쪽의 응답 시간 분포와 타임아웃 값별 거짓 타임아웃 비율), 기한 줄(C가 느릴 때 B와 C의 헛일).
> 노트북 한 대(24코어, 36GB)에서의 **상대 비교**다(명세 2절). 문서에 넣을 수치는 task 06에서 서버로 다시 잰다.

## 0. 모든 실험에 같게 두는 것

- 사슬·코드·이미지: 실행마다 `config.env`의 `git_commit`, `images.txt`.
- 자원: 서비스마다 CPU 2·메모리 768m, PostgreSQL CPU 2·1g(`compose.yaml` — task 01과 같다. 바꾸지 않는다).
- Tomcat 최대 스레드 200·큐(accept count) 100·최대 연결 8192, Hikari 풀 10·대기 1000ms, 연결 타임아웃 500ms(두 구간), keep-alive 클라이언트 15s < 서버 20s, 재시도 없음.
- 워밍업(장애 없음 20/s × 15s, 모두 201인 회차가 나올 때까지 최대 3회차) → 세 DB와 카운터·시각 기록·표본을 비움 → 부하 → 처리 중인 요청이 0이 될 때까지 기다림 → 내보내기 → 분석. `scripts/run.sh` 그대로.
- **조건 하나 = 서비스를 그 조건의 설정으로 다시 띄움**(환경 변수 → `scripts/up.sh`가 바뀐 컨테이너만 다시 만든다) → **버리는 실행 1회(`r0`)** → 반복 3회(`r1`~`r3`). 버리는 실행도 기록은 남긴다(표에는 넣지 않는다).
- 조건이 실제로 걸렸는지: 실행마다 `settings-<서비스>.json`(떠 있는 객체에서 읽은 값)의 요청 타임아웃과 가상 스레드 여부를 실행 스크립트가 그 조건의 값과 견주고, 다르면 실행 실패.
- 지연은 장애 헤더 `X-Fault: payment:delay=<ms>`로 넣는다(task 01의 장치 — 결제 서비스가 입구에서 그만큼 잔 뒤 처리한다). 넣은 수와 서비스가 센 수의 대조(task 01 분석기)도 그대로 한다.

## 1. 새로 재는 것과 지표의 식

형식과 판정 규칙의 정본은 `docs/measurement.md` 7절(이 절은 요지).

- **층마다의 시각 기록**: 각 서비스가 업무 입구에 든 요청마다 한 줄 — 입구에 든 시각 `start`, 입구를 나간 시각 `end`(μs, 서버의 벽시계), 응답 상태, 아래 층을 불렀으면 부른 시각 `callStart`·돌아온 시각 `callEnd`·결과(`Completed` / `Failed:<까닭>` / `Unknown:<까닭>`). 세 서비스와 k6가 한 컴퓨터의 같은 시계를 쓴다.
- **표본**: 각 서비스가 100ms마다 처리 중인 업무 요청 수(`inflight`), Tomcat 실행기의 바쁜 스레드 수(`active`)·스레드 수·큐에 기다리는 작업 수(`queue`), 연결 수를 메모리에 적는다(가상 스레드 실행기는 `active`·`queue`가 없다 — `null`).

| 지표 | 식 |
|---|---|
| 타임아웃(구간 U→L) | U의 시각 기록 가운데 결과가 `Unknown:REQUEST_TIMEOUT`인 것의 수 |
| **거짓 타임아웃**(U→L) | 타임아웃 가운데 L의 DB에 그 requestId의 처리 행(inventory `RESERVED`, payment `APPROVED`)이 있는 것의 수 |
| 거짓 타임아웃 비율 | 거짓 타임아웃 ÷ U가 L을 부른 수 |
| 불린 쪽 응답 시간 | L의 `end − start`(ms) 분위수 · U가 잰 `callEnd − callStart` 분위수 |
| 위 층이 포기한 시각 `giveUp(L)` | L 위의 층들이 그 요청을 포기한 시각 가운데 가장 이른 것: 구간 U→L′(L′는 L 자신이나 L과 U 사이의 층)의 결과가 타임아웃이면 U의 `callEnd`, k6가 응답을 받지 못했으면(`status` 0) `sentAt + elapsedMs` |
| **헛일**(층 L) | `end(L) > giveUp(L)`인 요청의 수(`wasted`), 그 가운데 L이 처리 행을 커밋한 수(`wastedProcessed`), 시간 `end(L) − max(start(L), giveUp(L))`의 합과 분위수 |
| 바쁜 스레드·큐(실험 나) | 주문 서비스 표본의 `active`·`queue`·`inflight`의 최대, `active`가 최대 스레드(200)에 닿은 표본 수 × 100ms |
| 가벼운 조회(실험 나) | `GET /orders/{requestId}`(결제를 부르지 않는 주문 서비스의 조회)를 느린 구간 앞·안·뒤로 나눠 응답 시간 분위수와 실패 수(200이 아니거나 응답 없음) |
| 회복 시간(실험 나) | ① 표본: 느린 구간이 끝난 뒤 주문 서비스의 `inflight + queue`가 느린 구간 전의 최댓값을 넘은 마지막 표본의 시각 − 느린 구간의 끝 ② 클라이언트: 느린 구간이 끝난 뒤 보낸 요청(지연 없는 사슬 요청과 조회) 가운데 "나쁜" 것(성공이 아니거나 1000ms보다 오래 걸림)의 마지막 `sentAt` − 느린 구간의 끝. 없으면 0 |

느린 구간의 시작·끝 = 느린 라벨(`payment:delay=5000`)로 보낸 요청의 `sentAt` 최소·최대.

## 3. 실험 가 — 거짓 타임아웃

- **바꾸는 것 하나**: 재고→결제 요청 타임아웃.
- **같게 두는 것**: 주문→재고 5000ms(가장 긴 재고→결제 값보다 길게 — 주문이 먼저 포기하지 않게), k6 요청 타임아웃 10s, 플랫폼 스레드, 넣는 지연(아래 — 씨앗이 같아 조건과 반복마다 요청 i의 지연이 같다).
- **부하**: 40/s × 30s = 1200건(constant-arrival-rate).
- **넣는 분포**: 결제 지연 = `max(1, round(80 · exp(0.6 · Z)))` ms, Z ~ N(0,1) — 로그정규, 가운데값 80ms. 요청 i의 Z는 씨앗 `20261124`와 i로 만든 의사 난수(mulberry32 + Box–Muller, `load/chain.js`). **지어낸 분포다** — 실제 결제의 응답 시간이 아니다.
  - 이론 분위수: p50 80ms, p90 173ms, p99 323ms, p99.9 ≈ 511ms. 실제로 뽑힌 1200개의 분위수는 분석기가 정답에서 다시 센다(`delays.payment`).

| 조건 | 재고→결제 타임아웃 | 넣은 분포의 분위수 |
|---|---|---|
| 가-1 | 80ms | p50 |
| 가-2 | 173ms | p90 |
| 가-3 | 323ms | p99 |
| 가-4 | 2000ms | "사실상 없음"(이론상 넘을 확률 ≈ 4×10⁻⁸) |

- **지표**: 재고→결제의 타임아웃·거짓 타임아웃 비율, 결제의 응답 시간 분포(`end − start`), 결제의 헛일.
- **예상(보기 전에)**:
  - 결제는 넣은 지연 뒤 DB에 한 번 쓰고 끝나므로 재고가 끊어도 결제 행은 남는다 → **타임아웃은 모두 거짓 타임아웃**이다(두 수가 같아야 한다 — 다르면 측정 도구를 먼저 의심).
  - 거짓 타임아웃 비율 ≥ 넣은 지연이 타임아웃 이상인 비율(가-1 ≈ 50%, 가-2 ≈ 10%, 가-3 ≈ 1%, 가-4 = 0). 결제의 처리 자체(몇 ms)와 네트워크가 더해지므로 **조금 더 크게** 나올 것이다 — 그 차이가 "불린 쪽 응답 시간 = 넣은 지연 + 처리"의 처리 몫이다.
  - 반복 사이의 차이는 작을 것이다(지연이 같다). 경계에 걸린 요청(지연 ≈ 타임아웃)만 흔들린다.
  - 결과가 이와 다르면(예: 가-4에서 0이 아님) 도구나 설정을 먼저 의심한다.

## 4. 실험 나 — 느린 아래 층이 위 층에 주는 영향

- **바꾸는 것**: (1) 타임아웃 — "사실상 없음"(주문→재고 60000ms, 재고→결제 60000ms) / "있음"(task 01 값: 주문→재고 2000ms, 재고→결제 1000ms). 둘을 한 쌍으로 바꾼다(실험의 질문이 "타임아웃이 없을 때와 있을 때"라서). (2) 스레드 — 플랫폼(기본) / 가상(`VIRTUAL_THREADS=true`). 2 × 2 = 네 조건, 한 번에 하나만 다른 짝끼리 견준다.
- **같게 두는 것**: 부하, 느린 구간, k6 요청 타임아웃 20s, 자원 제한.
- **부하**: 사슬 `POST /orders` 60/s × 50s = 3000건. 요청 번호 600~1799(0s 기준 10s~30s에 보내는 것)에 `payment:delay=5000` — 느린 구간 20s 동안 **모든 결제가 5s 늦는다**. 나머지는 장애 없음. 함께 가벼운 조회 `GET /orders/{id}` 10/s × 50s = 500건(결제를 부르지 않는다).
- **스레드가 차는 크기**: 느린 구간에 각 층이 요청 하나를 붙잡는 시간 ≈ 5s(타임아웃 없을 때) → 동시에 필요한 스레드 ≈ 60 × 5 = 300 > 200. 타임아웃이 있으면 주문·재고가 붙잡는 시간 ≈ 1s → 60개 — 주문은 차지 않고, 결제는 여전히 5s씩 자므로 결제의 스레드는 찬다.

| 조건 | 타임아웃(주문→재고 / 재고→결제) | 스레드 |
|---|---|---|
| 나-1 | 60000 / 60000ms | 플랫폼 |
| 나-2 | 2000 / 1000ms | 플랫폼 |
| 나-3 | 60000 / 60000ms | 가상 |
| 나-4 | 2000 / 1000ms | 가상 |

- **지표**: 주문 서비스의 `active`·`queue`·`inflight`의 최대와 200에 닿은 시간, 조회의 응답 시간과 실패(앞·안·뒤), 회복 시간 ①②, 사슬 요청의 응답 판정(완료·실패·결과 모름).
- **예상(보기 전에)**:
  - 나-1: 주문의 `active`가 200에 닿고 `queue`가 쌓인다. 조회도 같은 스레드를 기다리므로 느린 구간에 응답 시간이 초 단위로 늘고 일부는 k6 20s에 끊긴다. 느린 구간이 끝나도 쌓인 큐를 비울 때까지(수 s~수십 s) 회복하지 않는다.
  - 나-2: 주문의 `active`는 200에 닿지 않는다(≈ 60). 조회는 느린 구간에도 거의 그대로. 다만 **결제는 여전히 찬다**(타임아웃은 부른 쪽만 놓아준다) → 결제의 큐에 밀린 요청이 느린 구간 뒤에도 재고의 1s 타임아웃을 넘겨 "결과 모름"이 이어질 수 있다 — 회복 시간 ②가 0이 아닐 수 있다.
  - 나-3·나-4(가상): 잠자는 요청이 스레드를 붙잡지 않으므로 `queue`가 없고 조회는 느린 구간에도 거의 그대로일 것이다. 대신 처리 중 요청 수(`inflight`)는 나-3에서 ≈ 300까지 오른다. 다른 자원(Hikari 풀 10, 연결 수)이 먼저 막히면 그 사실을 적는다.
  - 플랫폼과 가상의 차이가 반복 사이의 흔들림보다 작으면 "가를 수 없다"고 쓴다.

## 5. 실험 다 — 나눈 타임아웃과 헛일

- **바꾸는 것**: 두 구간의 타임아웃의 배치.
- **같게 두는 것**: 부하, 넣는 지연, k6 10s, 플랫폼 스레드.
- **부하**: 20/s × 40s = 800건. 요청 i의 결제 지연 = `[없음, 500, 1500, 2500][i % 4]`ms(종류마다 200건) — 지어낸 섞음. 동시에 필요한 스레드 ≈ 20 × 2.5 = 50(차지 않는다 — 헛일만 본다).

| 조건 | 주문→재고 | 재고→결제 | 뜻 |
|---|---|---|---|
| 다-1 | 2000ms | 1000ms | 아래 구간이 위 층 안에 든다 |
| 다-2 | 1000ms | 2000ms | 아래 구간이 위 층보다 길다 |

- **지표**: 층마다 헛일의 수·처리 행을 커밋한 수·시간(합, 분위수), 구간마다 거짓 타임아웃.
- **예상(보기 전에)** — 결제는 위에서 끊어도 멈추지 않는다(취소가 전해지지 않는다):

| 지연 | 다-1 | 다-2 |
|---|---|---|
| 없음·500 | 헛일 없음 | 헛일 없음 |
| 1500 | 재고가 1000에 포기 → 결제 헛일 ≈ 500ms. 재고는 1000에 끝나 주문에 504 — 재고의 헛일 없음 | 주문이 1000에 포기, 재고는 1500까지 기다려 `RESERVED` → 재고 헛일 ≈ 500ms, 결제 헛일 ≈ 500ms, 주문→재고 거짓 타임아웃 |
| 2500 | 결제 헛일 ≈ 1500ms | 주문이 1000에 포기, 재고는 2000에 포기 → 재고 헛일 ≈ 1000ms, 결제 헛일 ≈ 1500ms |

  - 합: 다-1은 결제 ≈ 200 × (500 + 1500) = 400s, 재고 0. 다-2는 결제 ≈ 400s(같음), 재고 ≈ 200 × (500 + 1000) = 300s. **나눈 타임아웃(다-1)이 줄이는 것은 가운데 층(재고)의 헛일이고, 맨 아래(결제)의 헛일은 줄이지 못한다**는 것이 예상이다 — 그것을 줄이는 것은 기한·취소 전파(task 05)다.
  - 다-2에서 주문은 "결과 모름"인데 재고·결제는 처리됐다 → 주문→재고 구간의 거짓 타임아웃 ≈ 200(1500짜리).
