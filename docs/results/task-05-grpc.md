**스모크에서 드러난 것 — 설계에 반영했다**: 위 ②의 실행(`runs/slow-layer-20261125T112438-r1`)이 전송 대조에서 **불일치로 끝났다**(종료 2): 결제가 받은 gRPC 호출 3000건 가운데 시각 기록은 2657건. 나머지 343건은 결제의 실행기 큐에서 기다리는 동안 재고가 1000ms에 끊은 호출로, grpc-java가 처리 코드를 부르지 않았다(grpc-core 1.84.1 `ServerCallImpl.ServerStreamListenerImpl.halfClosed` — 호출이 취소됐으면 돌아간다). 그래서 그 343건은 넣은 지연도 세지 않았다(대조 분석의 장애 수 불일치 — 결제 `delay` 넣은 1200, 센 857). 이 뒤에 서버가 그런 호출을 따로 세게 했고(`grpcCancelledBeforeHandler`), 전송 대조의 규칙을 "센 수 = 기록 수 + 그것"으로 고쳤고, 가라앉기가 큐에서 기다리는 호출까지 기다리게 했다(`/inflight` — `docs/measurement.md` 11-4). 그 실행은 고치기 전의 코드라 다시 분석하지 않았다. 같은 실행에서 결제의 헛일은 857건(모두 처리 행 커밋), 그 가운데 위가 포기한 뒤에 시작한 일 **1건**이었다 — task 02 나-2(HTTP, 같은 부하와 타임아웃 — 다만 그때 코드와 다르고 다른 날이다)는 1568~1572건이었다. 한 번 본 것이고 반복하지 않았다(아래 "말할 수 없는 것").

## 이 자료로 말할 수 있는 것

**정해지는 값과 재는 값을 가른다**(설계 7절):

- **정해지는 값**(산수 — 도구와 조건이 규칙대로 걸렸다는 확인): 헛일 건수(400, 처리 200·400·0), 헛일 시간 합의 크기(≈ Σ(넣은 지연 − 경로의 가장 짧은 타임아웃)), "기한 전파는 P1에서 아무것도 바꾸지 않는다", G1의 `cancelAfterGiveUpMs` ≈ 1000ms(재고의 2000 − 주문의 1000), `overSlack` 800·0. 이 값들은 이 섞음과 이 타임아웃 값에서 나오며 일반화할 크기가 아니다.
- **재는 값**과 그것이 말하는 것(이 스택, 이 부하, 노트북, 3회):
  1. **취소는 아래 층에 1ms 안에 닿았다** — gRPC 서버가 그 호출의 취소를 안 시각 − 위가 포기한 시각의 가운데값 0.13~0.85ms, 최대 0.6~12.4ms(G1·G2·G3, 두 배치). HTTP 경로(이 구현의 Tomcat + 서블릿)에서는 아래 층의 처리 코드가 위의 포기를 알 길이 없다(잴 수 없음).
  2. **취소가 닿아도 처리 코드가 보지 않으면 헛일은 줄지 않았다** — G2(P2)에서 결제는 400건 모두 취소를 알았고(`cancelSeen` 400, 0.8ms 안에) 그 뒤로도 가운데값 520~890ms를 더 일해 400건 모두 커밋했다. 헛일 합은 404.6~413.6s로 H(405.5~406.2s)·G1(403.4~405.2s)과 범위가 겹친다 — **가를 수 없다**.
  3. **기한 전파(G2)가 줄인 것은 가운데 층(재고)의 헛일이다** — P2에서 재고의 헛일 합 304.2~306.8s(H·G1) → 2.5~6.9s(G2), 재고가 처리 행을 커밋한 것 200 → 0, 주문 → 재고의 거짓 타임아웃 200 → 0. 재고는 받은 기한에 결제 호출이 끊겨 행을 `UNKNOWN`으로 마쳤다(그 일에 취소를 안 뒤 가운데값 6.6ms). 다만 결제가 처리했으므로 **클라이언트는 결과 모름인데 결제 행이 있는 요청은 400 그대로**다 — 재고의 행이 `RESERVED`에서 `UNKNOWN`으로 바뀌었을 뿐 사슬의 끝(결제)은 처리됐다.
  4. **처리 코드가 취소를 보면(G3) 맨 아래 층의 헛일이 거의 없어졌다** — 두 배치에서 결제의 헛일 합 401.6~406.2s → 84~369ms(건당 1ms 안), 처리 행 400 → 0, 클라이언트는 결과 모름인데 결제 행이 있는 요청 400 → 0. 취소를 안 뒤 멈추기까지 가운데값 0.07~0.11ms. G3의 헛일 건수가 400보다 적은 것(P1 334~349, P2 395~398)은 결제가 멈춘 때(`end`)가 위가 포기한 때(재고의 `callEnd`) 이전인 기록이 있어서다(`end ≤ giveUp`이면 헛일로 세지 않는다). 왜 결제가 먼저 끝났는지(받은 기한의 타이머와 부른 쪽의 타이머·스레드 깨어남의 차례)는 가르지 않았다. 이 몫은 재는 값이지만 헛일의 크기에는 의미가 없다(건당 1ms 안).
  5. **전파된 기한은 0.7ms 늦게 세워졌다** — G2·G3(P2) 결제가 받은 기한 − 재고가 받은 기한의 가운데값 0.696~0.725ms(받은 쪽이 "받은 때 + 남은 시간"으로 다시 세우므로 전달 시간만큼 늦다).
  6. **H와 G1** — P1의 결제 헛일 합은 H 402.9~403.5s, G1 401.6~402.0s로 범위가 겹치지 않았다(G1이 합에서 약 1s, 건당 약 2.5ms 짧다). P2의 결제도 H 405.5~406.2s, G1 403.4~405.2s로 겹치지 않았다. P2의 재고는 겹친다(가를 수 없다). 차가 건당 수 ms이고, 그 차는 **프로토콜 하나의 차가 아니다**(한계 1).
- 조건 사이의 차가 큰 칸(헛일 합 400s 대 0.1~7s, 처리 행 400·200 대 0)은 반복 사이의 흔들림(최대 9s — P2-G2 r2)보다 훨씬 크다.

## 이 자료로 말할 수 없는 것

- **아래 층이 찼을 때**: 이 실험의 부하(동시 처리 ≈ 50)는 실행기를 채우지 않아, "포기한 뒤에 시작한 일"(`startedAfterGiveUp`)이 모든 조건에서 0이다. 그래서 G3의 "남은 기한이 없으면 시작하지 않는다"가 막는 몫, grpc-java가 큐에서 취소된 호출을 부르지 않는 몫(스모크에서 3000건 가운데 343건)은 이 자료로 크기를 말할 수 없다. 스모크의 한 번(task 02 나-2와 같은 부하 — 결제가 찬다)에서 그 몫이 HTTP와 크게 달라 보였지만(위가 포기한 뒤 시작한 일 1건 대 task 02의 1568~1572건) 한 번이고 코드와 날이 다르다 — 반복해서 재야 한다.
- 실제 DB 쿼리·외부 호출의 취소: G3의 처리 코드가 멈춘 것은 **넣은 지연(잠)** 동안뿐이다. 트랜잭션 안에서는 취소를 보지 않는다(설계 3절). 실제로 느린 층은 CPU·DB·잠금에서 느려지며, 그 일을 멈추는 비용과 시간은 여기서 잰 0.1ms와 다를 것이다.
- 기한 전파·취소가 **다른 배치**(경로의 가장 짧은 타임아웃이 서로 다른 둘 밖), 다른 섞음, 다른 부하에서 주는 차이. 결과 모름이 실패로 바뀌지 않는 이 규칙(설계 2절)에서 `UNAVAILABLE`의 갈래는 보정도 실험도 보지 않았다.
- 클라이언트 쪽의 이득: 이 실험의 클라이언트 응답(완료 400·결과 모름 400 — P1·P2 모두)은 조건 사이에 같다. 기한·취소는 아래 층의 헛일과 "결과 모름인데 처리됨"을 바꿨을 뿐 위의 결과를 바꾸지 않았다.
- 서버(task 06)에서의 값, 다른 gRPC 구현(grpc-kotlin, 서블릿 위의 gRPC, 다른 언어)의 값.

## 한계

1. **H와 G1의 차는 프로토콜 하나의 차가 아니다** — HTTP 경로는 Tomcat(NIO 커넥터 + 실행기, HTTP/1.1, 연결 하나에 요청 하나씩)과 JDK `HttpClient`, gRPC 경로는 Netty 서버(이벤트 루프 + 따로 둔 고정 실행기, HTTP/2 한 연결에 여러 스트림)와 grpc-java 채널이다. 스레드 모델·연결 방식·직렬화(JSON 대 protobuf)·관측(gRPC의 관측 인터셉터는 껐다 — HTTP 쪽 Spring MVC의 관측 설정은 바꾸지 않았고 켜져 있는지 확인하지 않았다)이 함께 바뀐다.
2. **취소를 보는 처리 코드는 직접 짠 것이다** — 넣은 지연을 문맥의 취소를 기다리며 자는 것(`GrpcDeadlines.awaitDelay`)으로, 흉내 낸 일에서의 효과다. 실제 DB 쿼리나 외부 호출의 취소와 다르다(위).
3. **노트북의 상대 비교** — 세 서비스(각 CPU 2)·PostgreSQL·k6와 다른 프로젝트의 컨테이너가 CPU를 나눠 썼다(load average 4.4~36.4). ms 단위의 값(취소가 닿는 시간, H와 G1의 차)은 서버에서 다를 수 있다(task 06).
4. **값 몇 개** — 조건마다 3회, 부하 하나, 배치 둘, 지연 네 값의 섞음 하나. 3 대 3에서 범위가 겹치지 않는 것은 차이가 없어도 10% 일어난다 — H와 G1의 건당 수 ms의 차는 그 정도의 근거다.
5. 시각은 한 컴퓨터의 같은 시계에 기댄다(`docs/measurement.md` 7-5). 받은 기한(`deadlineUs`)은 받은 쪽이 다시 세운 값이다.
6. 스모크 실행(`slow-layer`, 한 번)은 고치기 전의 코드였다 — 결과 표에 넣지 않았고 다시 분석하지 않았다.
7. 이 task의 테스트(설계 9절의 입구, `docs/measurement.md` 11절의 분석기)는 아직 없다 — 구현을 보지 않는 워커가 쓴다. 기존 테스트 1229개는 이 코드에서 모두 통과했다(`scripts/test.sh`).
