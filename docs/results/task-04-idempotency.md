바꾼 것: 키 끔/켬. 같게 둔 것: 40/s × 20s = 800건, 재시도 꺼짐, 칸 10개(정상 400, 주문이 2000ms에 포기하는 재고 `slow-first` 80, 층마다 커밋 뒤 끊김 80씩, 재고가 1000ms에 포기하는 결제 `slow-first` 80). 가라앉은 뒤 결과 모름을 같은 키로 20/s로 다시 보냈다.

| 키 | 결과 모름(다시 보낸 것) | 다시 보낸 것의 2xx | 그 가운데 저장한 응답 | 주문의 이어 하기 | 끝 상태: 세 층에서 정확히 한 번 / 둘 이상 / 빠진 층 | 두 번 처리됨(전체) |
|---|---|---|---|---|---|---|
| 끔 | 400 | 400 | 0 | 0 | **0** / 400 / 0 | 400 |
| 켬 | 400 | 400 | 80 | 320 | **400** / 0 / 0 | 0 |

**예상과의 대조**: 설계 8절의 표와 건수까지 같다(세 반복 모두) — 섞음과 규칙이 정한 값이다. 이 실험이 보인 것은 수가 아니라 **정확성**이다: 키가 있으면 결과 모름 400건이 같은 키로 다시 보낸 뒤 세 층 모두 정확히 한 번으로 모였고(주문에서 끊긴 80건은 저장한 응답, 나머지 320건은 주문이 같은 업무 행으로 아래 층을 다시 불러 아래 층의 저장한 응답이나 이어 하기로), 키가 없으면 다시 보낸 400건 모두 응답은 성공(201)인데 DB는 두 번 처리됐다.
- 이 실험에는 "아직 처리 중인 키에 다시 보냄(409)"이 없다 — 다시 보내기 전에 가라앉기(처리 중 0)를 확인했기 때문이다. 처리 중일 때 맞추면 어떻게 되는지는 실험 가-2·나가 보인다(409).

## 키가 있을 때 두 번 처리됨 — 조건마다

| 실험·조건 | 끔 | 켬 | 켬에서 0이 아닌 까닭 |
|---|---|---|---|
| 보정 `cal-idem` | 350 | 0 | — |
| 가-1 · 가-2 | 122 · 198 | 0 · 0 | — |
| 나 잇달아 · 동시에 | 400 · 400 | 0 · 0 | — |
| 다 | 0 | 0 | (장애·중복 없음) |
| 라 | 400 | 0 | — |

키가 있을 때 두 번 처리됨은 모든 실행에서 0이었다. 대신 켬에서 새로 생긴 것: 실험 가-2의 "클라이언트는 실패, 아래 층은 처리"(43~45건)와, 쓸모없는 위 층의 재시도(주문→재고 278 → 365).

## 하네스 문서의 "잴 것"에 대해 — 이 결과가 말하는 것과 말하지 못하는 것

### 멱등 키 줄 — "키가 없을 때 재시도·중복 요청이 만드는 이중 처리 건수, 키가 있을 때 0건인지"

- **말하는 것**: 커밋 뒤 끊김(결과 모름)과 처리 뒤 늦은 응답(`slow-first`)을 재시도하면 키가 없을 때 그만큼 두 번 처리됐고(가-1 122, 가-2 198 — 층마다 재시도하면 더), 클라이언트가 같은 요청을 잇달아·동시에 두 번 보내면 모두 두 번 처리됐다(나 400/400). 업무 행과 같은 트랜잭션에 키를 넣으면 이 모든 경우에 DB로 센 두 번 처리됨이 0이었다(키 행과 업무 행의 짝이 모든 실행에서 맞았다). 동시에 온 같은 키는 PostgreSQL의 유일 제약이 줄 세워 하나만 처리됐다(400쌍에서 399~400쌍이 409, 나머지는 저장한 응답).
- **말하지 못하는 것**: 실제 장애·중복의 빈도(섞음은 지어낸 것이라 건수는 그 섞음의 그림이다). 키를 다른 저장소(캐시)에 두거나 다른 트랜잭션에 둘 때(재지 않았다 — 그때는 "같은 트랜잭션의 확인"이 성립하지 않는다). 처리 중에 죽은 요청의 키(회수를 넣지 않았다).

### 동시에 온 같은 키 — "기다리나, 거절하나"

- **말하는 것**: 거절(409)을 고르면, 위 층이 409를 "처리 안 된 실패"로 읽는 한 **위 층의 재시도가 아래 층의 처리 중인 키에 부딪혀 실패로 끝나고 아래 층은 끝내 처리한다**(가-2 켬 43~45건 — 클라이언트는 실패, 결제는 승인). 또 아래 층이 실패를 저장해 돌려주면 위 층의 재시도가 쓸모없어진다(가-2에서 키가 없을 때 살던 87건이 실패로 굳고, 주문의 재시도는 278 → 365로 늘었다). 즉 **멱등 키의 상태 규칙(무엇을 저장해 되돌려 주나)과 위 층이 409·저장한 실패를 어떻게 읽나는 함께 정해야 한다** — 이 실험은 그 둘을 따로 정했을 때의 대가를 쟀다.
- **말하지 못하는 것**: 기다리는 방식(재지 않았다), 위 층이 409를 "결과 모름"으로 읽고 다시 시도할 때, 실패를 저장하지 않고 이어 하게 할 때 — 각각 가-2의 수를 바꿀 것이지만 재지 않았다. 주문의 재시도 간격(100ms)과 타임아웃(250ms)이 아래 층의 재시도 시간과 겹치는 이 배치 밖의 몫.

### 키 저장의 비용 줄 — "키 저장이 더하는 쓰기 지연"

- **말하는 것**: 장애 없는 40/s에서 층 자기 몫의 p50이 주문 +1.9ms, 재고 +1.1ms(가를 수 있음), 결제 +0.5ms(가를 수 없음) — 쓰기가 둘인 층이 하나인 층보다 더 늘었다. 클라이언트 응답 시간의 p50·p90·p99는 반복 사이의 범위가 겹쳐 **가를 수 없었다**.
- **말하지 못하는 것**: 무거운 부하·큰 표(키가 수백만 개일 때의 인덱스)·느린 디스크에서의 비용, 서버에서의 절댓값(task 06). 조건을 섞어 돌리지 않아 차례의 몫을 가르지 못했다.

### 결과 모름을 나중에 맞추기 줄

- **말하는 것**: 결과 모름(커밋 뒤 끊김, 위 층의 타임아웃)을 같은 키로 나중에 다시 보내면, 키가 있고 "결과를 몰랐던 층은 같은 업무 행으로 아래 층을 다시 부른다"는 규칙이 있을 때 400건 모두 세 층에서 정확히 한 번으로 모였다. 키가 없으면 응답은 모두 성공인데 400건 모두 두 번 처리됐다 — **응답만 보고 맞췄다고 할 수 없다**.
- **말하지 못하는 것**: 실패(502)로 저장한 요청을 맞추는 것(이 규칙에서는 저장한 502가 돌아와 맞출 수 없다 — 가-2의 43건이 그 꼴이다). 다시 보낼 때까지의 시간이 길 때(키의 만료), 처리 중일 때 맞추기.

## 한계

- **노트북 한 대**, 실행 중 같은 컴퓨터의 다른 부하는 재지 않았다. 건수가 세 반복에서 같은 실험(가-1, 가-2 끔, 나의 셋, 라)은 섞음과 규칙이 정한 값이라 잡음이 없었다는 근거가 아니다. ms 값(실험 다)과 시각에 달린 몫(가-2 켬의 `fail-first=2`, 나 동시에·켬의 갈래)만 흔들림이 드러날 수 있고, 그 크기를 3회로 말할 수 없다.
- **조건의 차례**: 모든 실험에서 끔 → 켬 차례로 돌렸다(섞지 않았다) — 실험 다의 차에 차례의 몫이 섞였을 수 있다.
- **장애는 헤더로 넣은 것**이고 끊김은 Tomcat 내부에 기댄다(`docs/idempotency.md` 7절). 실제 네트워크 끊김(패킷 유실, 반쯤 닫힌 연결)과 같다고 확인하지 않았다 — 위 층에서 `IOException`(JDK)·`status` 0(k6)으로 보이는 것만 확인했다.
- **멱등 키의 규칙 하나**만 쟀다: 키 = requestId, 금액만 견줌, 처리 중이면 409, `COMPLETED`·`FAILED`는 저장한 응답, `UNKNOWN`은 이어 하기. 다른 규칙의 결과는 위 "말하지 못하는 것".
- `laterArrivalStatus`는 주문의 입구에 든 시각으로 나중을 가린다 — 409를 받는 쪽은 키를 넣은 차례로 정해지므로 이 지표는 "둘째"를 가리키지 않는다(실험 나).
- k6가 요청마다 새 연결을 맺는다(`--no-connection-reuse`). 동시에 두 번(`http.batch`)의 두 요청이 주문에 드는 차이는 따로 재지 않았다.
