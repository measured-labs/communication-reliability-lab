## 1. 목표·대상 (필수)

주문→재고→결제의 동기 호출 사슬에서 타임아웃, 재시도, 멱등 키, 기한 전파의 선택이 실패·중복·지연·부하에 주는 차이를 재서, 하네스 문서 `communication-reliability.md` 2절(동기 호출)의 "잴 것"을 실측으로 채울 수 있게 한다. 대상은 이 저장소(`communication-reliability-lab`)뿐이다.

## 2. 경계·불변식 (필수)

- **재는 것이 맞는지부터 확인한다**: 측정 도구(부하, 정답 기록, 대조 분석)는 답을 아는 보정 실행에서 유실 0건·중복 0건·건수 일치를 내야 한다. 보정을 통과하지 못한 도구로 잰 수치는 결과로 쓰지 않는다.
- **한 실험은 한 가지만 바꾼다**: 비교하는 조건 밖의 것(부하 모양, 데이터, 머신 배치, 버전)은 같게 둔다. 바꾼 것과 같게 둔 것을 실행 기록에 남긴다.
- **원시 기록을 남긴다**: 실행마다 설정, 요청별 정답과 결과, 서비스의 DB 상태를 남기고, 보고의 모든 수치는 그 기록에서 다시 계산할 수 있어야 한다. 반복 횟수와 편차를 함께 적는다.
- **"두 번 처리됨"과 "잃음"은 응답이 아니라 DB의 상태로 판정한다**(주문 수, 재고 수, 결제 건수와 금액).
- 타임아웃으로 결과를 모르는 요청은 성공이나 실패로 세지 않고 따로 센다.
- 재시도, 백오프, 예산, 멱등 키는 **직접 짠 최소 코드**로 넣는다(라이브러리의 기본 동작이 아니라 규칙을 재려는 것이다). 라이브러리와의 비교는 이 작업의 범위 밖이다.
- 노트북에서 잰 수치는 상대 비교로만 쓰고, 문서에 넣을 수치는 서버에서 잰 것만 쓴다.

- 라이브러리와 프레임워크의 동작은 공식 문서를 열어 확인한다(버전을 적는다).

## 4. 금지영역 (필수)

- 이 저장소 밖을 고치지 않는다(`failure-alert-lab`, `http-grpc-lab`, 하네스 저장소 포함 — 읽기만).
- 이 컴퓨터와 서버의 다른 프로젝트의 Docker 자원·프로세스·포트를 건드리지 않는다. `docker system prune` 금지. 서버의 상주 컨테이너를 건드리지 않는다.
- 서버 접속 정보는 사용자에게 묻는다(파일을 뒤져 찾지 않는다). 비밀 값을 기록이나 커밋에 옮기지 않는다.
- 강제 push를 하지 않는다. 이 저장소 밖의 원격 저장소에 쓰지 않는다(이 프로젝트의 원격 저장소 생성과 push는 7절의 허가 범위에 든다).
- 서버에 올리거나 서버에서 실행하는 것은 올리기 전에 배치와 쓸 자원을 보이고 확인받는다.

## 5. 검증 방법 (필수)

- 보정 실행(답을 아는 실행)이 통과한다 — task 01.
- 측정 도구의 분석기는 단위 테스트를 둔다(명세에서 출발 — 구현자와 다른 워커). 일부러 유실·중복을 넣은 기록을 주면 그 수를 낸다.
- 실험마다: 조건당 반복 실행(횟수는 task 01의 편차를 보고 정해 사용자에게 알린다), 원시 기록 보존, 결과 표와 한계.
- 코드 리뷰는 강도대로(중간 — 듀얼 1패스). 결과 문서는 수치를 원시 기록에서 다시 계산해 대조한다.

## 6. stakes (필수)

**중간.** 새 프로젝트라 깨질 기존 동작은 없지만, 결과 수치가 하네스 분기 문서의 근거가 된다(틀린 측정이 조용히 기준으로 굳는 것이 가장 큰 손실). 서버에서의 실행은 사용자 확인을 거친다.

## 7. 자율성

- 모드: **auto**(11-23 23:56)
- 새 의존성·새 기술을 더할 때(11-23 23:56): **처음 설계에서 필요한 라이브러리와 기술을 늘어놓아 최대한 정하고**(아래 "의존성 목록" — 사용자 확인), 그 뒤 구현하면서 더 필요해진 것은 메인이 정하고 기록한다. 기록에는 정말 필요한가, 왜 필요한가, 선택지마다의 장점과 단점, 고른 것과 이유를 적는다(log "진행 중 결정"과 `docs/dependencies.md`). 하네스의 "덜 만드는 순서"대로 먼저 없이 되는지 본다.
- 허가 범위(11-23 23:56, 사용자: "4번에 대해서 생성과 푸시까지도 자동으로 진행하고"): 이 프로젝트의 원격 저장소 생성과 이 저장소의 브랜치 push까지 묻지 않고 한다. 들지 않는 것(늘 묻는다): 강제 push, 다른 저장소, 이슈·릴리스, 서버에 올리거나 서버에서 실행하는 것(4절).

## 8. load-bearing 가정

1. 세 서비스와 DB, 부하 도구를 노트북 한 대에서 함께 돌려도 조건 사이의 상대 차이는 드러난다 — task 01의 보정과 기준 실행에서 반복 사이의 편차로 확인한다.
2. 장애(느린 응답, 실패, 죽임)를 요청 단위로 정확히 넣을 수 있다 — task 01에서 넣은 수와 관측한 수를 대조한다.

## 9. task 분해

### task 01 — 뼈대와 측정 도구

- **결과**: 주문→재고→결제가 HTTP로 이어지는 세 서비스와 DB가 로컬에서 뜨고, 장애를 요청 단위로 넣을 수 있고, 측정 도구가 보정 실행을 통과한다.
- 다음 task에 주는 영향: 모든 실험이 이 도구로 잰다. 반복 횟수의 근거(편차).
- **계약**(11-24 00:13 메인이 풀어 적음):
  - 사슬: `order`(A) → `inventory`(B) → `payment`(C). 주문이 재고를 부르고 재고가 결제를 부른다 — **호출의 깊이를 셋으로 만들려는 실험용 구조이고 실제 설계의 권고가 아니다**(README에 밝힌다). 서비스마다 자기 DB(PostgreSQL 한 인스턴스, 데이터베이스 셋).
  - 요청마다 부하 도구가 만든 `requestId`가 세 서비스의 행에 남는다. 판정은 DB의 행으로 한다(주문·재고 예약·결제 — `requestId`마다 행의 수와 상태).
  - 장애는 요청 헤더로 넣는다: 어느 서비스에서, 무엇을(정한 시간만큼 늦춤 / 오류 응답 / 처리한 뒤 응답 전에 실패). 헤더는 사슬을 따라 그대로 넘어간다. 넣은 수와 서비스가 센 수를 대조할 수 있어야 한다.
  - task 01의 호출은 타임아웃을 설정에 명시하고(기본값에 기대지 않는다) 재시도하지 않는다. 숨은 기본값("의존성 목록" 아래)을 끄거나 명시하고, 껐다는 것을 실행 기록에 남긴다.
  - 측정 도구: 부하 스크립트(k6, 정해진 도착률)가 요청마다 정답 한 줄(requestId, 넣은 장애, 받은 응답이나 타임아웃)을 남긴다 → 실행 스크립트가 세 DB의 상태를 내보낸다 → 분석기(Kotlin)가 둘을 대조해 요청마다 완료 / 실패 / 결과 모름으로 가르고 잃음·두 번 처리됨·건수 일치를 낸다. 입력과 출력의 형식은 `docs/measurement.md`에 적는다.
  - 보정 실행: 답을 아는 섞음(정상, 층마다의 오류, 타임아웃보다 짧은 지연, 타임아웃보다 긴 지연)을 보내 분석기의 결과가 기대와 건수까지 같아야 한다. 같은 실행을 세 번 반복해 편차를 적는다.
  - 실행 한 번의 기록은 `runs/<시나리오>-<시각>-r<번호>/`에 남긴다(설정, 정답, DB 상태, 보고).
  - 검증: 분석기의 단위 테스트는 구현자와 다른 워커가 `docs/measurement.md`와 이 계약에서 쓴다(잃음과 두 번 처리됨을 일부러 넣은 기록을 주면 그 수를 낸다).

### task 02 — 타임아웃

- **결과**: 타임아웃 값에 따른 거짓 타임아웃의 비율과, 타임아웃이 없을 때·있을 때 느린 아래 층이 위 층에 주는 영향(묶이는 스레드, 관련 없는 요청의 실패)을 잰다. 구간마다 미리 나눈 타임아웃이 위 층이 포기한 뒤의 헛일을 얼마로 막는지 잰다.
- **계약**(11-24 02:07 메인이 풀어 적음 — 노트북에서의 상대 비교. 문서에 넣을 수치는 task 06에서 서버로 다시 잰다):
  - **실험 가 — 거짓 타임아웃**: 맨 아래 층(결제)의 처리 시간을 요청마다 정해진 분포에서 뽑아 넣고(부하 스크립트가 뽑아 정답에 남긴다 — 씨앗을 고정해 반복마다 같은 값), 재고→결제의 요청 타임아웃을 여러 값으로 바꿔 가며, **끝내 처리됐는데 부른 쪽은 타임아웃으로 끊은 요청의 비율**을 잰다. 타임아웃 값은 넣은 분포의 분위수에 맞춰 고른다(값과 분위수를 함께 적는다).
  - **실험 나 — 느린 아래 층이 위 층에 주는 영향**: 결제가 느려진 구간을 두고(부하의 일부 시간 동안 모든 결제가 길게 늦는다), 타임아웃이 사실상 없을 때(아주 긴 값)와 있을 때를 견준다. 재는 것: 주문 서비스의 바쁜 스레드 수와 대기 중인 요청 수의 시간 흐름, **결제를 부르지 않는 요청**(주문 서비스의 가벼운 조회 끝점 — 이번 task에서 하나 더한다)의 응답 시간과 실패 수, 느린 구간이 끝난 뒤 정상으로 돌아오기까지의 시간. 부하는 스레드가 차는 크기로 잡고, 차지 않으면 그 사실을 결과에 적는다. 플랫폼 스레드가 기본이고, 가상 스레드로 같은 실험을 한 번 더 한다.
  - **실험 다 — 나눈 타임아웃과 헛일**: 주문→재고와 재고→결제의 타임아웃을 (1) 아래 구간이 위 층 안에 들게 나눈 경우와 (2) 아래 구간이 위 층보다 긴 경우로 두고, **위 층이 포기한 뒤에도 아래 층이 계속한 일**(건수와 시간 — 층마다 요청의 시작·끝 시각과 위 층이 포기한 시각으로 계산)을 잰다.
  - 이번 task에 더하는 것: 요청마다의 지연을 분포에서 뽑는 부하 스크립트, 층마다 처리의 시작·끝 시각 기록, 바쁜 스레드 수·대기 수를 일정 간격으로 뜨는 기록, 주문 서비스의 조회 끝점, 시나리오와 기대 파일, 분석기의 새 지표와 그 문서. 재시도·멱등 키는 넣지 않는다.
  - 조건당 3회 반복, 새로 띄운 직후에는 버리는 실행 한 번. 결과는 `docs/results/task-02-timeouts.md`에 표(조건, 반복마다의 값, 가운데값과 범위)와 한계로 적고, 모든 수치가 `runs/`의 기록에서 다시 계산된다.

### task 03 — 재시도

- **결과**: 재시도 횟수별 성공률과 지연, 백오프와 지터가 있을 때·없을 때의 몰림과 회복 시간, 한 층에서만 재시도할 때와 층마다 재시도할 때 맨 아래의 요청 배수, 재시도 예산이 있을 때·없을 때의 부하를 잰다.
- **계약**(11-24 13:40 메인이 풀어 적음 — 노트북에서의 상대 비교):
  - 재시도는 **직접 짠 최소 코드**로 아래 층 호출을 감싼다(라이브러리 없음). 설정으로 켜고 끈다: 층마다의 최대 시도 횟수, 다시 시도하는 실패의 종류(일시적 실패와 타임아웃), 간격(없음 / 고정 / 지수 백오프 / 지수 백오프 + 지터 — 지터의 방식은 하나로 정해 적는다), 재시도 예산(토큰 버킷 — 부르는 쪽 프로세스 전체). 기본은 모두 꺼짐(task 01·02의 동작 그대로). 실제로 쓰인 값이 `/settings`에 나온다.
  - 일시적 실패를 넣는 법: 요청마다 "처음 몇 번의 시도는 실패한다"를 부하 스크립트가 정해진 분포에서 뽑아 헤더로 넣는다(씨앗 고정, 정답에 남긴다). 구간 장애(일정 시간 동안 모든 호출이 실패)도 헤더와 시각으로 넣는다. 서비스는 시도마다 넣은 장애를 센다.
  - **실험 가 — 시도 횟수**: 재고→결제의 최대 시도를 1·2·3·5로 바꿔 가며, 끝내 성공한 비율, 응답 시간의 분위수, 결제가 받은 호출 수(요청 수에 대한 배수)를 잰다.
  - **실험 나 — 간격**: 결제가 일정 시간 동안 모두 실패했다가 돌아오는 구간에서, 간격 네 가지마다 결제가 받는 호출의 시간 흐름(짧은 간격으로 나눈 수 — 몰림의 꼭대기), 구간이 끝난 뒤 정상으로 돌아오기까지의 시간, 구간 동안 결제가 받은 호출 수를 잰다.
  - **실험 다 — 어느 층에서**: (1) 재고만 재시도 (2) 주문만 재시도 (3) 주문과 재고가 모두 재시도 — 결제가 받은 호출 수의 배수, 끝내 성공한 비율, 다시 한 일(재고가 다시 처리한 횟수)을 잰다. 주문의 타임아웃이 아래 층의 재시도를 품을 만큼 길 때와 짧을 때를 나눠 적는다.
  - **실험 라 — 재시도 예산**: 긴 구간 장애에서 예산이 있을 때와 없을 때, 결제가 받은 호출 수와 그 시간 흐름, 구간 뒤의 회복, 예산 때문에 재시도하지 못한 수를 잰다.
  - 이번 단계는 멱등 키가 없다 — **재시도가 만든 "두 번 처리됨"을 조건마다 그대로 세어 적는다**(task 04의 출발점). 결제가 처리한 뒤 응답이 늦어 부른 쪽이 다시 부른 경우가 여기에 든다.
  - 측정 도구: 시도마다의 기록(어느 요청의 몇 번째 시도, 시작·끝, 결과, 기다린 간격)과 그것을 쓰는 분석(`docs/measurement.md`에 정의). **서버에 닿지 못한 요청이 0이 아니면 실행이 실패한다**(task 02에서 드러난 빈 곳). 이번 단계의 모든 시나리오는 부하 도구의 연결 재사용을 끈다(task 02의 실험 나와 같게 — 결과에 밝힌다).
  - 설계 문서(예상을 실행 전에 커밋) → 새 지표의 보정 → 조건당 3회와 버리는 실행 → `docs/results/task-03-retries.md`. 모든 수치는 커밋한 원시 묶음에서 다시 계산된다.

### task 04 — 멱등 키

- **결과**: 멱등 키가 없을 때 재시도와 중복 요청이 만드는 이중 처리 건수와, 키가 있을 때 0건임을 DB 상태로 확인하고, 키 저장이 더하는 쓰기 지연을 잰다. 결과를 모르는 요청을 같은 키로 나중에 맞추는 것이 되는지 확인한다.

### task 05 — gRPC

- **결과**: 같은 사슬을 gRPC로도 잇고, 기한과 취소 전파가 미리 나눈 타임아웃(HTTP)보다 헛일을 얼마나 줄이는지 잰다.

### task 06 — 서버에서 재기와 결과 문서

- **결과**: task 02~05의 실험을 서버에 나눠 올려 다시 재고, 하네스 문서의 "잴 것"마다 실측을 대는 결과 문서를 쓴다. 서버 배치는 올리기 전에 확인받는다.
